# v44 — 높은 실내 시야와 직접 고르는 좌석

## 실내 시야

사용자의 후속 요청은 실내 카메라가 너무 낮고 가까우며, 앉고 싶은 위치를 직접 고르고 싶다는 것이다. 실외 기본 시야(0.48rad / 16.5m)는 유지한다. 실내 첫 방문은 **yaw 0.5rad, pitch 0.65rad(37.2도), 거리 15m, FOV 50도**를 사용한다. 같은 방에서 걷거나 시설을 이용할 때 자동으로 이 값으로 돌아가지 않는다. 방에서 수동으로 바꾼 시야는 기억하고, 나가면 저장한 실외 시야를 복구한다.

료칸의 기존 천장 7.2m는 높은 각도에서 거리 축소를 강제했다. `interiorRooms.ryokan.ceiling`을 11.5m로 올리고 협업 변경의 실제 벽·보·지붕도 이 값에 맞춘다. 천문대 ceiling은 기존 28m다.

기존 료칸 입장 z8.5에서는 남쪽 벽이 가까워 거리 요청을 늘려도 실제 카메라 거리가 짧았다. 입장 위치만 **(400, 5.3)**으로 3.2m 안쪽의 중앙 보행홀로 옮긴다. 문·출구·외관의 좌표는 유지한다. 클라이언트와 서버의 region 입장 모두 같은 `interiorRooms.entry`를 사용한다. 입장 화면 전환 안에서 위치와 시야를 바꾼다.

수치 검증에서 두 실내 입장 시점 모두 room 경계 안의 실제 거리 15m를 유지한다. 오마카세 세 좌석에서도 14.8m 이상을 유지하며 pitch는 바뀌지 않는다. 벽 옆 벤치처럼 공간이 충분하지 않은 경우에는 기존 충돌 회피가 필요한 만큼 거리를 줄인다. 장애물을 관통하거나 각도를 바꾸어 넓은 시야를 꾸미지 않는다.

완성된 료칸 mesh로 `buildInteriors → room 경계 제한 → cameraClearance → setCamera`를 적용한 추가 수치도 확인했다. 입장 실제 거리는 **15.000m**, 오마카세 좌석 0·1·2의 실제 거리는 각각 **14.921m**, pitch는 모두 **0.650rad**다. 새 지붕·보·등이 이 네 기본 구도를 추가로 축소하지 않았다. 이 결과는 실제 geometry 교차 검사이며 GPU 화면을 렌더한 결과는 아니다.

## 직접 선택하는 자리

- 오마카세 세 자리와 공유 벤치 두 자리에 각각 명시적 선택 버튼을 제공한다. 버튼은 현재 카메라에 투영된 좌석 순서로 **왼쪽 / 가운데 / 오른쪽**을 표시한다. 두 자리 벤치는 왼쪽 / 오른쪽이다.
- 서버 presence의 좌석 점유 상태를 반영하여 이용 중인 자리는 비활성화한다. 키보드 E/F/G도 비활성 버튼을 실행할 수 없다.
- 실제 의자·벤치의 좌석 표면을 탭해도 해당 자리 번호를 선택한다. 이 선택은 현재 공간과 접근 가능 거리 안에서만 작동한다. 실제 scene mesh가 시선을 막으면 벽 뒤 좌석을 선택하지 않는다. 렌더링 패스나 매 프레임 picking 루프는 추가하지 않는다.
- 안내 접근점에서 4.5m 이내이거나 실제 선택 좌석에서 3.2m 이내인 위치를 접근 범위로 인정한다. 의자 바로 앞에 있는데 안내 기준점까지 돌아가야 하는 상황을 피한다. 실제 좌석 위치는 서버가 가진 공유 데이터에서 구한다.
- 클라이언트의 점유 표시는 안내다. 최종 결정은 서버의 원자적인 INSERT와 좌석·방·visitor 유일성 제약으로 한다.
- 같은 의자를 동시에 선택하면 한 사람만 앉는다. 나머지는 `seat_occupied`와 “다른 자리를 선택해 주세요” 안내를 받는다. 빈 옆자리로 자동 배정하지 않는다.
- 동일 visitor의 동일 자리 재시도는 기존 예약을 돌려준다. 다른 자리를 요청하면 먼저 일어나야 한다. 클라이언트에서 다른 실제 의자를 고를 때는 기존 자리를 반환한 뒤 새 자리 예약을 요청한다.
- 관람차·리프트의 기존 두 사람 자동 합승 배정은 유지한다. 오마카세의 단일 셰프 순서, 임대 갱신·만료 복구, 서버 시각 기반 서빙은 그대로 유지한다.

## API 계약

```json
{"kind":"dining","seat":2}
```

```json
{"kind":"bench","benchId":"ryokan-tea-bench","seat":1}
```

`seat`는 정수다. dining은 0–2, bench는 0–1만 허용한다. 누락·문자열·소수·범위 밖 값은 400 `seat_required`다. `cabin`, 좌석 좌표, 다른 사용자의 id는 클라이언트 입력으로 결정하지 않는다. 점유 경합은 409 `seat_occupied`, 현재 예약과 다른 자리 요청은 409 `already_seated`다. 성공 응답의 reservation 필드는 기존 계약을 유지한다.

일반 인증, 현재 월드, region 검사와 API의 기존 접근 제한을 유지한다. 별도 DB migration은 필요하지 않다. 기존 `ride_seats`와 오마카세 확장 migration을 재사용한다. 개인 데이터나 좌석 데이터를 초기화하지 않는다.

## 변경 파일 및 검증

주요 구현은 `camera-policy.js`, `park.js`, `interior-layout.js`, `ride-seats.js`, `winter-experience.js`, `seat-selection.css`, `server/ride-api.js`다. `social.js`에서는 `reserveRide(kind, benchId, seat)`의 인자와 payload만 확장했다. `index.html`·SW 연결과 실내 실제 건축 geometry는 협업 담당자가 통합한다.

관련 테스트는 다음을 검증한다.

- 첫 입장·실내 재방문·실외 복귀의 시야와 실제 room 경계 거리.
- 모든 입장/출구와 실내 활동의 보행 가능 위치·연결.
- 명시적 dining/bench 좌석의 동시 경합, 재시도, 점유 충돌, 범위 밖 값, 다른 공간/먼 위치 거절.
- 기존 서버 presence의 정확한 pose, 대기 좌석 갱신, 만료 후 일어나기 복구.
- 좌석 버튼과 키보드 비활성, 점유 경합 안내, 직접 의자 hit plane, 요청 중 떠난 후 늦은 응답 처리.
- 실제 DOM·Three scene을 사용하는 앱 통합 시나리오. GPU 렌더러만 stub이므로 화면이 예쁘게 보이는지 검증한 것은 아니다.

2026-11-18 최종 focused 실행은 **54개 통과, 실패 0개**다. 이 실행의 `runtime.test.mjs`는 실제 카메라에서 오른쪽 오마카세 의자를 화면 좌표로 투영하여 pointer 이벤트로 탭하고, 서버 transport를 대신하는 stub에 `seat:2`가 전달되어 캐릭터가 실제 x414 좌석에 앉는 것까지 검증했다. 별도 실내 동선·geometry를 포함한 관련 실행도 62개가 통과했으며 두 실행의 테스트들은 상당 부분 중복된다. 코드 구문 검사와 `git diff --check`가 통과했다.

```sh
node --experimental-vm-modules --test tests/camera-policy.test.mjs tests/shared-rides.test.mjs tests/ryokan-service.test.mjs tests/winter-experience.test.mjs tests/social-ui.test.mjs tests/runtime.test.mjs
```

WebGL을 생성할 수 없는 현재 환경에서 실제 3D 구도와 모바일 체감, 실제 기기 FPS는 **UNKNOWN**이다. 수치·서버·입력 검증을 육안 확인이나 GPU 성능 측정으로 바꾸어 보고하지 않는다.
