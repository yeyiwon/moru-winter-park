# v39 성능 범위

이번 변경은 접속 권한과 단일 월드 라우팅이다. 월드 Geometry·조명·VFX·LOD·렌더 DPR은 변경하지 않았다. 초대 해시 인덱스와 방문자/초대/차단 JOIN을 사용하고, 기존 presence 주기와 최대 12명 정책을 유지한다.

v39 FPS·GPU·메모리·실물 모바일 전후 비교는 **UNKNOWN**. 자동 검사/실제 브라우저 기능 성공은 성능 향상 수치가 아니다. 아래 v38 측정과 장면별 한계를 이전 버전 기록으로 보존한다.

# v38 성능 측정

## 환경과 방법

Mac Apple M2, Chrome 157, 같은 격리 로컬 서버와 게스트 방. PC 1280×800 / DPR 1, 모바일 에뮬레이션 390×844 / 기기 DPR 3 / 렌더 DPR 1.25. 비교 시 수동 high, 동일 production 변환, 같은 GPU query와 장면 순서, 각 6초 표본을 사용한다. 이전은 운영 `0720494`, 이후는 최종 v38 코드다. 자동 품질·DPR 변화의 영향을 제거하기 위한 제한된 비교이며 실물 휴대폰 결과가 아니다.

실제 게임 animate callback을 측정한다. 평균 FPS, p95/p99, callback CPU, GPU timer, draw calls/triangles, Geometry 추정 바이트, JS heap, 초기 진입 시간을 JSON에 기록한다. Geometry 추정량은 GPU 총점유량이 아니다. GPU 드라이버의 전체 메모리 점유량은 UNKNOWN.

## 결과

평균 FPS / p95 frame ms. PC 료칸은 전환 완료를 기다린 별도 재측정값이다.

| castle | 27.4 → 28.8 | 50.0 → 50.0 | 57.7 → 40.6 | 16.8 → 33.4 |
| ski | 29.1 → 30.3 | 50.0 → 50.0 | 52.6 → 44.8 | 33.4 → 33.4 |

트리의 PC GPU 평균은 24.63→15.30ms, 삼각형은 456만→430만, draw call은 458→432였다. 모바일 트리 57.2→59.7fps, 군중 36.2→38.4fps였지만 **모바일 성 57.7→40.6, 스키 52.6→44.8fps로 느린 표본도 관측**됐다. 해당 구역 CPU callback 시간은 감소했으나 GPU 시간은 증가했다. 후속 확인 시 호스트 iCloud 동기화 프로세스가 약 85% CPU를 사용하고 있었다. 이것이 편차의 유일한 원인이라고 확정하지 않으며, 모든 구역의 성능 개선을 주장하지 않는다.

첫 PC 료칸 표본은 async 입장 완료 전 캡처를 시작해 34fps/낮은 p95라는 불일치가 있었다. profiler가 입장 Promise를 기다리도록 고쳐 같은 설정으로 재측정한 결과 60.0→59.8fps였다. 원래 JSON도 보존하며 steady-state 수치로 사용하지 않는다.

초기 준비 시간은 PC 11.24→13.08초, 모바일 크기 8.89→8.95초. **로딩 시간 단축은 확인되지 않았다.** 최초 생성/컴파일 지연은 남은 병목이다. 그래픽 품질 자동 조정, 선명도 하한과 입력 안정성이 이번 최적화의 주된 개선이며, 수동 high에서 모든 장면의 60fps를 보장하지 않는다.

원시 자료: `qa/browser-v38/{pc,mobile}-controlled-{before,after}.json`, `pc-room-{before,after}.json`. GPU/CPU/p99/draw calls/triangles/heap/버퍼 수와 실제 DPR이 포함된다. 품질 설정의 목표 DPR과 별도로 비교용 실제 renderer DPR을 강제로 고정했다.

이전 자동 모드 측정은 [customization-mobile-v38.md](customization-mobile-v38.md)에 별도로 보존한다. 자동 모드의 다른 화질/운영체제 부하 조건에서 나온 수치를 순수 코드 성능 향상으로 해석하지 않는다.

## 한계

- 짧은 단일 측정이며 OS 부하와 shader cache에 영향을 받는다. FPS가 비슷한 장면에서도 높은 선명도와 하위 프레임을 함께 본다.
- 초기 WebGL/큰 월드 생성은 메인 스레드에서 실행되는 구간이 남아 있다. 로딩 재시도·timeout 정합성 개선이 초기화 전체의 비동기화를 뜻하지 않는다.
- 실물 iOS Safari/Android GPU, 발열·배터리·30분 이상 안정성 UNKNOWN.
- 기존 outdoor 영역의 완전한 자산 streaming은 미구현이다. 실내 lazy loading/해제, 공간별 컬링과 LOD를 사용한다.

## 자동 품질 · 꼬리 착용 12인 연속 실행

최종 production 변환 / 390×844 DPR 3 에뮬레이션 / 본인+원격 11명 / 고양이 귀·꼬리 / 180초. 평균 **50.46 FPS**, p95 **33.4ms**, p99 **49.9ms**, GPU 평균 **9.42ms**, draw calls 평균 **712**. 프레임 측정 중 실제 render DPR은 1을 유지하며 자동 품질은 medium에서 low로 내려갔다. 이는 12인 고화질 60fps의 증거가 아니라 부하에 반응하는 품질 조정의 실측이다.

시작→끝 Geometry 개수 673→673, texture 19→17, Geometry 바이트 추정 225,273,740→224,731,532, JS heap 446,070,206→382,897,402. 셰이더 program은 71→132로 늘었다(품질/광원 조합 변경 중 variant 컴파일). 이 한 번의 3분 결과만으로 장시간 누수가 없다고 단정하지 않는다. 원격 11명은 시작/끝 모두 유지됐고 page/scenario 오류 0건. `qa/browser-v38/tail-soak.json`.

별도 옵션 반복 검사에서는 워밍업 뒤 GPU buffer 생성 수가 173→173으로 유지됐다. 자원 해제 자동 검사는 선택했던 눈·귀·소품까지 정확히 한 번 해제하는지 확인한다.
