## 확인한 원인

- 마시멜로 트럭은 중심점의 지면 높이만 사용했다. 중심 약74m에 비해 뒤쪽 설면이 최대 약84m여서 모델이 눈 속에 묻혔다. 모델을 공중으로 올리지 않고 바닥 전체와 서비스 접근로를 지지하는 평탄한 구역을 만들었다.
- 기존 유카타 소매는 정적 몸통 메시였지만 팔은 매 프레임 별도의 인스턴스 행렬로 움직였다. 같은 팔 자세 데이터를 사용하도록 수정했다.
- 오로라는 큰 접힘과 여러 가산 레이어가 겹쳐 밝은 덩어리가 되었다. 곡면의 되접힘과 발광 누적을 줄였다.
- 관람차의 위치/좌석/서버 좌표가 여러 파일에 숫자로 중복되어 있었다. 순수 공유 배치 파일로 통합하여 모델과 서버의 좌석 및 방향을 일치시켰다.
- 성을 키운 뒤 기존 산책로가 새 날개 건축물과 기존 시설에 걸리는 구간을 자동 검사에서 찾아 우회 곡선을 조정했다. 단순히 새 모델만 놓지 않았다.

## 검증

모델/동작 검사에는 성 중앙 통로 전체, 실제 기하에 대한 성 가림 여부, 관람차 전회전 수평/두 좌석 방향/캐릭터 공간, 서버와 모델 좌표 일치, 다리 착지와 이동 경로, 트럭 바퀴 아래 실제 렌더 지형, 모든 슬로프의 조작/완주, 유카타 로컬·원격 팔 자세를 포함한다.

UI 검사에는300×260,300×350,334×460,560×200,760×510 지도 영역에서6개 레이블의 터치 영역 비겹침, 실제 좌표 왕복 투영, 한 번 누르기/드래그 구분, 로딩의 실제 단계·오류·종료, 모바일 관람차에서 두 모루의 전체 영역이 카메라 안에 들어오는지를 포함한다.

성 모델은9 Mesh, 전체 장면은594 Mesh/215 material/약313만 삼각형이다. 성 리본을 품질별3개 묶음으로 최적화했으며, 각 품질의 형상·색·위상은 병합 전후 같은 삼각형 데이터로 검증했다. 관람차는69 Mesh/3 material/135,136삼각형이다. 이 수치는 CPU 기하 검사이며 모바일 GPU FPS를 의미하지 않는다.

전체 검사 **236/236 통과** 후 작은 지도 영역에 대한 추가 검사를 수행했다.

최종 실행 명령: `npm test`, `npm run build`, `npm run build:vercel`, `git diff --check`.

**브라우저 검증 한계:** 이번 v26 작업에서는 브라우저 제어 도구를 사용할 수 없었다. 실제 브라우저에서 최종 셰이더 모습, 모바일 실기기 터치, 2개 브라우저의 동시 탑승을 확인했다고 주장하지 않는다. 자동 DOM/기하/통합 검사는 실제 WebGL 화면 검증과 구분한다. v25에서 찍은 화면을 이번 결과로 사용하지 않았다.
