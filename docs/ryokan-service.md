# 료칸 오마카세 · 공유 좌석과 서빙 검증

## 원인과 구조

오마카세는 기존 공유 좌석 시스템에 `dining` 시설을 추가해 세 명이 각자 카운터에 앉는 방식입니다. 기존 `ride_seats`의 SQL 제약은 모든 시설의 좌석을 `0,1`로 제한하므로 클라이언트와 API에 세 번째 좌석만 추가하면 실제 저장 과정에서 실패합니다.

`0016_dining_seats.sql`은 테이블을 증분 재작성해 `dining`에만 `0,1,2`를 허용합니다. 나머지 시설은 기존 `0,1` 제약을 유지합니다. 기존 행의 모든 열을 복사하고 `(room,kind,cabin,seat)` 기본키와 `visitor` 유일성을 유지합니다. 원래 마이그레이션 파일을 고치거나 기존 좌석 데이터를 삭제하지 않습니다. Drizzle schema·snapshot·journal도 함께 갱신했고 다시 generate를 실행해 추가 차이가 없음을 확인했습니다.

## 동작 계약

- 입장한 게스트가 료칸 내부의 카운터 가까이 있을 때 `/api/ride`에 `kind: dining`을 요청합니다.
- 같은 공간에는 세 자리만 예약됩니다. 네 번째 요청은 자리가 찼다는 응답을 받습니다. 같은 게스트의 동시 중복 요청은 같은 예약으로 합쳐집니다.
- `started_at`은 좌석을 얻은 시각과 앞 예약의 시작 시각 + 9초 중 늦은 값입니다. 한 번의 SQL 쓰기 안에서 시작 시각을 결정하므로 동시에 요청해도 셰프의 서빙 구간이 겹치지 않습니다.
- 공유 시작 시각을 기준으로 대기 → 인사 → 준비 → 서빙 → 건네기 → 식사 상태를 계산합니다. 뒤에 앉은 손님은 자기 순서를 기다립니다.
- 좌석은 기존 presence 요청으로 유효기간이 연장됩니다. 대기 중인 손님도 자기 좌석의 올바른 pose로 갱신합니다. 다른 손님의 좌석 좌표를 전송하면 서버가 거부합니다.
- 내리기, 료칸에서 나가기, 공간에서 나가기, 갱신 없이 유효기간 만료가 일어나면 자리를 다시 사용할 수 있습니다.
- `room`별 좌석 격리는 저장 계층에서 유지합니다. 이것이 사용자가 별도 방을 만들 수 있다는 뜻은 아닙니다. 실제 입장 라우터의 단일 공간 정책은 유지됩니다.

## 모바일 중단 후 좌석 만료 복구

독립 검토에서 잠든 모바일 탭의 좌석이 만료되면 `presence`의 409 응답 때문에 클라이언트가 계속 식사 pose를 보내고, 이후 다른 사람의 상태 갱신도 멈추는 문제를 확인했습니다.

서버는 예약 만료를 `RIDE_RESERVATION_EXPIRED`, 유효한 예약과 다른 좌석 좌표를 `RIDE_POSE_INVALID`로 구분합니다. 클라이언트는 만료 응답을 보낸 당시의 게스트 ID와 정확히 같은 예약 객체인 경우에만 `lab:ride-expired`로 한 번 일어납니다. 기존 `wake()`가 시설 상태를 정리하고 좌석을 해제합니다. 메뉴나 퀴즈로 렌더링이 멈춰 있어도 다음 `presence`는 `mode: ''`인 보행 상태로 다시 보냅니다. `park.js`의 `lab:stand` 처리도 보행 가능한 위치를 결정한 직후 pose를 발행합니다.

늦게 온 만료 응답은 새로 예약한 자리 또는 바뀐 게스트를 해제하지 않습니다. 401·403 입장 권한 종료는 기존 초대 화면 처리를 그대로 따릅니다. 좌석 만료만으로 다시 초대를 요구하지 않습니다.

## 변경 파일

구현은 `dist/ryokan-service.js`, `dist/ride-seats.js`, `server/ride-api.js`, `server/api.js`와 료칸 렌더링·활동 연결을 사용합니다. 좌석·서빙 구현을 검증하면서 스키마 제약과 만료 후 연결 복구를 보완했습니다.

스키마 수정은 `db/schema.js`, `drizzle/0016_dining_seats.sql`, `drizzle/meta/0016_snapshot.json`, `drizzle/meta/_journal.json`에 있습니다. 만료 복구 수정은 `server/api.js`, `dist/social.js` 및 `dist/park.js`의 즉시 보행 pose 발행에 있습니다. 검증은 `tests/ryokan-service.test.mjs`, `tests/social-ui.test.mjs`에서 수행합니다.

## 실제 검증

```sh
node --experimental-vm-modules --test tests/quiz-journal.test.mjs tests/quick-quiz.test.mjs tests/social-ui.test.mjs tests/ryokan-service.test.mjs
```

22개 테스트 통과. 임시 폴더의 실제 SQLite와 기존 로컬 DB 어댑터를 사용했으며 운영 DB와 개발자의 게스트 데이터는 사용하지 않았습니다. 기존 공유 좌석 회귀도 앞선 검증에서 통과했습니다.

오마카세 전용 8개 테스트에서 확인한 내용:

- 마이그레이션 전의 관람차·벤치·초급 및 상부 리프트 5행을 삽입하고 마이그레이션 후 모든 값이 같은지 확인.
- 세 번째 식사 좌석 허용, 다른 시설의 세 번째 좌석 거부, 잘못된 좌석·중복 방문자·동일 좌석 중복 거부.
- 동시 세 명 예약, 네 번째 거부, 독립 room, 동일 방문자의 중복 요청.
- 자리에서 나온 뒤 재사용, 이미 예약된 손님을 앞지르지 않는 서빙 시각, 정확한 만료 경계.
- 료칸이 아닌 지역·멀리 떨어진 위치·이미 다른 시설 이용 중인 요청 거부.
- 세 좌석의 위치, 서빙 단계의 시간 경계, 한 번에 한 손님만 서빙되는 순서.
- 실제 익명 입장 및 `handleAPI` 라우팅, presence의 대기 좌석 갱신·공유 시각 전파, 다른 좌석 위조·만료된 예약 거부, 내리기·실외 이동·퇴장 후 좌석 해제.
- 실제 Three.js 셰프 모델에 공유 시각·좌석을 주입해 대기 중 접시 숨김, 2.7초부터 준비 중 표시, 8초 건네기, 9초 이후 숨김, 예약 취소 시 즉시 숨김을 확인. 좌우 손님의 좌석 사이 이동 및 움직임 감소 상태에서 변환 행렬이 모두 유한한 값인지 확인.

추가 클라이언트 복구 테스트에서는 실제 `social.js`와 `winter-experience.js`를 함께 실행했습니다. 렌더링이 멈춘 상태에서 만료 응답을 받으면 일어나기와 해제가 각각 한 번 일어나고, 보행 pose로 연결이 정상화되는지 확인했습니다. 새 예약·다른 게스트가 된 후 도착한 만료 응답과 잘못된 좌석 좌표 오류가 현재 예약을 해제하지 않는지도 검증했습니다.

이 테스트는 서버/좌표/시간 계약과 Three.js 객체 상태를 검증합니다. 셰프가 실제 화면에서 자연스럽게 손을 움직이는지, 음식 전달의 시각적 완성도, 기기별 FPS와 네트워크 환경별 지연은 별도 브라우저 검증 대상입니다. 현재 검증 환경의 GPU 컴파일이 비활성화되어 셰이더의 실제 GPU 실행과 실물 모바일 성능 수치는 UNKNOWN입니다.
